# 13. Базовая архитектура системы

## 13.1 Цель раздела

Базовая архитектура определяет логическую структуру системы, основные компоненты и принципы их взаимодействия с учетом:

- бизнес-требований;
- функциональных требований;
- нефункциональных требований;
- выбранной событийно-ориентированной микросервисной архитектуры;
- критических бизнес-сценариев;
- выделенных атрибутов качества;
- ограничений и рисков реализации.

---

# 13.2 Основные архитектурные ограничения

| Ограничение | Архитектурное следствие |
|---|---|
| Глобальная аудитория пользователей | Необходимость горизонтального масштабирования и распределённой инфраструктуры |
| Большое количество пользователей | Сервисы не должны иметь единой точки отказа |
| Тренировки в различных местах и поездках | Необходимо обеспечить работу мобильного клиента при нестабильном сетевом соединении |
| Большое количество спортивных устройств | Необходим отдельный слой интеграции с внешними устройствами |
| Телеметрия во время тренировок | Необходимо поддерживать обработку большого количества событий |
| Массовые соревнования | Необходимо предусмотреть обработку пиковых нагрузок |
| Постепенное расширение функциональности | Сервисы должны развиваться независимо |
| Интеграция с существующими приложениями компании | Необходим отдельный интеграционный контур |
| Региональные промоакции | Необходимо учитывать регион пользователя при формировании предложений |
| Работа с пользовательскими данными | Необходимы централизованные механизмы аутентификации, авторизации и защиты данных |

---

# 13.3 Логическая структура системы

Базовая архитектура состоит из следующих логических уровней:

1. **Клиентский уровень**
   - мобильное приложение;
   - интерфейс пользователя.

2. **Уровень доступа к системе**
   - управление внешними запросами;
   - аутентификация;
   - авторизация;
   - маршрутизация запросов.

3. **Бизнес-сервисы**
   - пользователи;
   - тренировки;
   - устройства;
   - аналитика;
   - рекомендации;
   - социальные функции;
   - соревнования;
   - уведомления;
   - инвентарь.

4. **Событийный контур**
   - публикация событий;
   - доставка событий;
   - подписка сервисов на события;
   - асинхронное взаимодействие.

5. **Интеграционный контур**
   - спортивные устройства;
   - существующие приложения компании;
   - система промоакций;
   - внешние сервисы.

6. **Контур хранения данных**
   - независимые хранилища сервисов;
   - аналитическое хранилище;
   - данные пользовательской активности.

---

# 13.4 Основные компоненты

## 13.4.1 Мобильное приложение

Мобильное приложение является основной точкой взаимодействия пользователя с системой.

Основные функции:

- регистрация и вход;
- управление профилем;
- запуск тренировок;
- просмотр результатов;
- планирование тренировок;
- взаимодействие с сообществом;
- участие в соревнованиях;
- просмотр рекомендаций;
- получение уведомлений;
- управление подключёнными устройствами.

Приложение должно учитывать возможность тренировок при нестабильном сетевом соединении.

---

## 13.4.2 Сервис пользователей

Отвечает за управление пользователями и их профилями.

Основные функции:

- создание и изменение профиля;
- хранение пользовательских настроек;
- управление спортивными интересами;
- управление настройками приватности;
- предоставление данных другим сервисам через определённые интерфейсы.

Сервис является владельцем пользовательских данных.

---

## 13.4.3 Сервис тренировок

Является центральным бизнес-сервисом платформы.

Основные функции:

- создание тренировки;
- запуск и завершение тренировки;
- получение результатов;
- хранение истории;
- обработка данных тренировки;
- публикация событий о тренировочной активности.

Сервис является владельцем данных о тренировках.

---

## 13.4.4 Сервис интеграции со спортивными устройствами

Отвечает за взаимодействие с внешними спортивными устройствами.

Основные функции:

- подключение устройств;
- получение телеметрии;
- нормализация данных различных производителей;
- передача данных в систему;
- обработка ошибок подключения.

Выделение данного компонента позволяет изолировать различия API и протоколов различных производителей от основной бизнес-логики платформы.

---

## 13.4.5 Сервис аналитики

Отвечает за обработку накопленных данных о спортивной активности.

Используется для:

- анализа тренировок;
- определения динамики результатов;
- расчёта производных показателей;
- подготовки данных для рекомендаций;
- формирования аналитической информации.

---

## 13.4.6 Сервис рекомендаций

Формирует персональные предложения для пользователя.

Источниками информации являются:

- профиль пользователя;
- история тренировок;
- результаты активности;
- спортивные интересы;
- используемый инвентарь;
- региональные данные;
- доступные промоакции.

Результат работы сервиса может использоваться как для спортивных рекомендаций, так и для продвижения продукции компании.

---

## 13.4.7 Сервис соревнований

Отвечает за организацию и проведение спортивных соревнований.

Основные функции:

- создание соревнований;
- регистрация участников;
- получение результатов;
- расчёт рейтингов;
- определение итоговых результатов.

Сервис должен поддерживать горизонтальное масштабирование, поскольку соревнования могут создавать значительные пиковые нагрузки.

---

## 13.4.8 Социальный сервис

Отвечает за социальное взаимодействие пользователей.

Основные функции:

- поиск спортсменов;
- формирование групп;
- публикации;
- взаимодействие участников;
- организация совместных тренировок.

---

## 13.4.9 Сервис уведомлений

Отвечает за доставку уведомлений пользователям.

Источниками уведомлений могут быть:

- завершение тренировки;
- спортивные достижения;
- приглашения в группы;
- изменения соревнований;
- персональные рекомендации;
- промоакции и спортивные новости.

Сервис должен работать независимо от основных бизнес-процессов, чтобы отправка уведомлений не блокировала пользовательские операции.

---

## 13.4.10 Сервис спортивного инвентаря

Отвечает за информацию о спортивном оборудовании пользователя.

Используется для:

- хранения перечня инвентаря;
- учёта использования;
- определения необходимости обслуживания;
- формирования рекомендаций.

---

# 13.5 Взаимодействие компонентов

В архитектуре используются два основных типа взаимодействия.

## Синхронное взаимодействие

Используется в сценариях, где пользователь ожидает непосредственный ответ системы.

Примеры:

- получение профиля;
- просмотр истории тренировок;
- получение списка соревнований;
- просмотр группы;
- получение рекомендаций.

Для таких операций используется запрос-ответ.

---

## Асинхронное взаимодействие

Используется для операций, которые не требуют немедленного ответа пользователю или могут выполняться независимо.

Примеры:

- завершение тренировки;
- обработка телеметрии;
- обновление аналитики;
- расчёт достижений;
- обновление рейтинга соревнования;
- формирование рекомендаций;
- отправка уведомлений.

Событийное взаимодействие позволяет уменьшить связанность компонентов и масштабировать обработчиков независимо.

---

# 13.6 Основные события системы

В качестве примеров ключевых доменных событий могут использоваться:

| Событие | Источник | Основные потребители |
|---|---|---|
| `UserRegistered` | Пользователи | Рекомендации, аналитика, уведомления |
| `WorkoutStarted` | Тренировки | Аналитика |
| `WorkoutCompleted` | Тренировки | Аналитика, рекомендации, соревнования, уведомления |
| `TelemetryReceived` | Устройства | Тренировки, аналитика |
| `AchievementEarned` | Аналитика / геймификация | Уведомления, социальный сервис |
| `CompetitionResultUpdated` | Соревнования | Уведомления, клиент |
| `RecommendationGenerated` | Рекомендации | Уведомления, клиент |
| `PromotionAvailable` | Интеграционный контур | Рекомендации, уведомления |

События не должны содержать внутренние детали реализации сервисов. Они должны представлять бизнес-факт, который может быть интересен нескольким потребителям.

---

# 13.7 Принцип владения данными

Каждый бизнес-сервис является владельцем собственных данных.

Прямой доступ одного сервиса к базе данных другого сервиса не допускается.

Получение необходимых данных осуществляется через API или посредством обработки событий.

---

# 13.8 Обеспечение офлайн-работы

Поскольку приложение может использоваться во время поездок и тренировок в местах с нестабильным соединением, клиентская часть должна поддерживать ограниченный offline-first режим.

В offline-режиме приложение должно позволять:

- начать тренировку;
- продолжить тренировку;
- локально сохранять полученные данные;
- отображать уже загруженную информацию.

После восстановления соединения накопленные данные синхронизируются с серверной частью.

Таким образом, временная недоступность сети не должна приводить к потере данных тренировки.

---

# 13.9 Адресация атрибутов качества

Архитектурные решения должны быть непосредственно связаны с выбранными атрибутами качества.

## Масштабируемость

### Требование

Система должна поддерживать рост количества пользователей, тренировок и спортивных устройств, а также кратковременные пиковые нагрузки во время массовых соревнований.

### Архитектурные решения

- микросервисная архитектура;
- горизонтальное масштабирование;
- независимое масштабирование сервисов;
- асинхронная обработка событий;
- разделение потоков нагрузки между сервисами.

### Наиболее критичные компоненты

- сервис тренировок;
- сервис устройств;
- сервис соревнований;
- событийный контур.

---

# Доступность

### Требование

Отказ отдельного компонента не должен приводить к полной недоступности платформы.

### Архитектурные решения

- отсутствие единственного экземпляра критичных сервисов;
- горизонтальное масштабирование;
- асинхронное взаимодействие;
- изоляция сервисов;
- повторная обработка событий;
- локальное сохранение данных тренировки на клиенте.

### Наиболее критичные компоненты

- сервис тренировок;
- сервис пользователей;
- событийный контур;
- сервис уведомлений.

---

# Безопасность

### Требование

Необходимо защищать пользовательские данные и ограничивать доступ к функциональности системы.

### Архитектурные решения

- централизованная аутентификация;
- авторизация;
- разграничение доступа;
- изоляция данных сервисов;
- защищённое взаимодействие между компонентами;
- контроль доступа к персональным данным;
- аудит критичных операций.

### Наиболее критичные компоненты

- контур аутентификации и авторизации;
- сервис пользователей;
- API-контур;
- сервисы, содержащие персональные данные.

---

# Производительность

### Требование

Критические пользовательские операции должны выполняться с приемлемым временем отклика, а потоковые данные должны обрабатываться без существенных задержек.

### Архитектурные решения

- разделение синхронных и асинхронных операций;
- асинхронная обработка телеметрии;
- горизонтальное масштабирование;
- кэширование часто используемых данных;
- выделение ресурсоёмких операций в отдельные сервисы.

---

# Наблюдаемость

### Требование

Распределённая система должна позволять определять состояние компонентов и диагностировать ошибки.

### Архитектурные решения

Для каждого сервиса предусматриваются:

- технические логи;
- бизнес-метрики;
- технические метрики;
- распределённая трассировка;
- correlation ID;
- мониторинг обработки событий.

Особое внимание необходимо уделить цепочкам:

`Устройство → Тренировка → Аналитика → Рекомендации → Уведомление`

и

`Тренировка → Соревнование → Рейтинг → Уведомление`.

---

# 13.10 Адресация основных рисков

| Риск | Архитектурная мера |
|---|---|
| Рост количества пользователей | Горизонтальное масштабирование |
| Пиковая нагрузка во время соревнований | Независимое масштабирование и асинхронная обработка |
| Потеря телеметрии | Локальное накопление данных и повторная отправка |
| Отказ отдельного сервиса | Изоляция сервисов и повторная обработка событий |
| Дублирование событий | Идемпотентная обработка |
| Несогласованность данных | Eventual Consistency и определение владельца данных |
| Изменение API спортивного устройства | Выделенный сервис интеграции |
| Изменение внешних корпоративных систем | Изоляция интеграционного слоя |
| Сложность диагностики | Централизованное логирование, метрики и трассировка |
