# 14.2 Информационное представление

## 14.2.1 Назначение

Информационное представление описывает основные данные системы, отношения между ними, владельцев данных и основные информационные потоки.

В соответствии с принципами выбранной микросервисной архитектуры каждый бизнес-сервис является владельцем собственных данных.

---

## 14.2.2 Основные информационные сущности

| Сущность | Владелец | Основное содержание |
|---|---|---|
| User | Сервис пользователей | Идентификатор, профиль, настройки |
| SportProfile | Сервис пользователей | Спортивные интересы и параметры |
| Workout | Сервис тренировок | Данные тренировки |
| WorkoutTelemetry | Сервис тренировок / устройств | Телеметрические данные |
| Device | Сервис устройств | Подключённое устройство |
| Equipment | Сервис инвентаря | Спортивный инвентарь |
| Group | Социальный сервис | Спортивная группа |
| SocialActivity | Социальный сервис | Публикации и активность |
| Competition | Сервис соревнований | Параметры соревнования |
| CompetitionResult | Сервис соревнований | Результат участника |
| Achievement | Сервис достижений / аналитики | Спортивное достижение |
| Recommendation | Сервис рекомендаций | Персональная рекомендация |
| Promotion | Интеграционный контур | Промоакция |
| Notification | Сервис уведомлений | Уведомление пользователя |

---

## 14.2.3 Владение данными

Основной принцип:

> **Каждая бизнес-сущность имеет одного логического владельца.**

Другие сервисы не получают прямого доступа к хранилищу владельца.

Например:

```text
                   ┌──────────────┐
                   │    User      │
                   └──────┬───────┘
                          │
                   User Service
                          │
                          ▼
                    User Database


                   ┌──────────────┐
                   │   Workout    │
                   └──────┬───────┘
                          │
                  Workout Service
                          │
                          ▼
                  Workout Database
```

Это обеспечивает независимость сервисов и позволяет изменять внутреннюю модель данных без изменения остальных компонентов.

## 14.2.4 Основные информационные потоки

### Поток тренировочных данных

```text
Device
   │
   ▼
Device Service
   │
   ▼
Workout Service
   │
   ├──► Workout data
   │
   └──► WorkoutCompleted
                │
                ▼
             Event Bus
                │
       ┌────────┼─────────┐
       ▼        ▼         ▼
   Analytics  Competition Recommendation
```

```text

       │
       ▼

       │
       ▼

       │
       ▼
Recommendation Service
       │
       ▼

       │
       ▼
Notification Service
```

## 14.2.5 Согласованность данных

В распределённой архитектуре не предполагается использование единой транзакции между всеми сервисами.

Для большинства бизнес-процессов используется модель **eventual consistency**.

Например:

1. Тренировка завершается.
2. Сервис тренировок сохраняет результат.
3. Публикуется событие `WorkoutCompleted`.
4. Аналитика получает событие.
5. Сервис соревнований обновляет рейтинг.
6. Сервис рекомендаций пересчитывает рекомендации.
7. Сервис уведомлений формирует уведомление.

Таким образом, состояние различных подсистем может кратковременно отличаться, но в штатном режиме постепенно приводится к согласованному состоянию.
