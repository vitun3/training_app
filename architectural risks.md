# 15. Анализ рисков созданной архитектуры и архитектурных компромиссов

## 15.1 Назначение раздела

После формирования базовой архитектуры необходимо оценить, какие риски возникают вследствие принятых архитектурных решений и какие компромиссы были сделаны.

Цель анализа:

- определить потенциальные точки отказа;
- выявить риски, связанные с распределённостью системы;
- оценить влияние архитектурных решений на бизнес-цели;
- определить меры снижения рисков;
- зафиксировать осознанные архитектурные компромиссы.

---

# 15.2 Общая оценка архитектурных рисков

Выбранная событийно-ориентированная микросервисная архитектура позволяет решить основные задачи системы, однако переносит часть сложности из бизнес-логики отдельных приложений на инфраструктуру и взаимодействие между сервисами.

Основные категории рисков:

- распределённые взаимодействия;
- eventual consistency;
- рост количества сервисов;
- сложность эксплуатации;
- зависимость от Event Bus;
- обработка больших потоков телеметрии;
- пиковые нагрузки во время соревнований;
- интеграция с большим количеством внешних устройств;
- защита большого объёма пользовательских данных.

Наиболее существенными являются риски, способные одновременно повлиять на несколько ключевых атрибутов качества.

# 15.4 R-01. Отказ Event Bus

## Описание

Event Bus является центральным элементом асинхронного взаимодействия сервисов.

При его недоступности новые события не смогут своевременно передаваться между сервисами.

Это может привести к задержке:

- обновления рейтингов;
- формирования рекомендаций;
- расчёта достижений;
- отправки уведомлений.

При этом непосредственно сохранение тренировки может оставаться доступным.

## Меры снижения риска

- отказоустойчивое развертывание Event Bus;
- репликация;
- сохранение сообщений;
- повторная доставка;
- контроль lag;
- мониторинг состояния очередей;
- независимое масштабирование consumers.

---

# 15.5 R-02. Eventual Consistency

## Описание

Разделение данных между сервисами приводит к тому, что состояние различных компонентов может обновляться не одновременно.

Сервис тренировок может уже показать завершённую тренировку, в то время как рейтинг соревнования или рекомендация ещё не обновлены.

## Последствия

Пользователь может временно видеть:

- старое место в рейтинге;
- старую статистику;
- отсутствие только что полученного достижения;
- ещё не обновлённые рекомендации.

## Меры снижения риска

- явно определить допустимую задержку обновления;
- использовать идентификаторы событий;
- реализовать повторную обработку;
- обеспечить идемпотентность consumers;
- отображать пользователю время последнего обновления данных там, где это необходимо.

## Архитектурный вывод

Eventual consistency принимается как осознанный компромисс ради масштабируемости и независимости сервисов.

Для операций, требующих строгой согласованности, необходимо отдельно определить синхронный сценарий или владельца бизнес-транзакции.

---

# 15.6 R-03. Пиковая нагрузка во время соревнований

## Описание

В момент начала или завершения массового соревнования возможно резкое увеличение:

- количества запросов;
- количества тренировок;
- количества поступающих результатов;
- количества операций с рейтингом;
- количества уведомлений.

## Риск

Без специальной архитектурной поддержки нагрузка на сервис соревнований может повлиять на остальные компоненты.

## Меры снижения риска

- независимое горизонтальное масштабирование;
- асинхронная обработка результатов;
- очереди;
- partitioning событий;
- кэширование данных рейтинга;
- предварительное масштабирование перед известными соревнованиями;
- ограничение нагрузки на некритичные функции.
- пиковая нагрузка одного бизнес-сценария не должна приводить к отказу всей платформы.

---

# 15.7 R-04. Потеря или дублирование телеметрии

## Описание

Приложение предусматривает подключение сторонних устройств для отслеживания тренировок, включая различные сенсоры. :contentReference[oaicite:3]{index=3}

При этом возможны:

- потеря сетевого соединения;
- временная недоступность устройства;
- повторная отправка данных;
- нарушение порядка сообщений;
- частичная передача тренировки.

## Меры снижения риска

На стороне мобильного клиента:

- локальное накопление данных;
- повторная отправка;
- идентификатор тренировки;
- последовательные номера сообщений.

На серверной стороне:

- идемпотентная обработка;
- дедупликация;
- контроль порядка сообщений;
- подтверждение обработки.

---

# 15.8 R-05. Усложнение эксплуатации

## Описание

Микросервисная архитектура приводит к увеличению количества независимо работающих компонентов.

Вместо одного приложения необходимо эксплуатировать:

- несколько бизнес-сервисов;
- Event Bus;
- базы данных;
- интеграционный слой;
- инфраструктуру мониторинга;
- инфраструктуру логирования;
- компоненты безопасности.

## Последствия

Увеличиваются:

- количество точек мониторинга;
- количество возможных отказов;
- сложность диагностики;
- требования к DevOps/SRE;
- стоимость инфраструктуры.

## Меры снижения риска

- автоматизация развёртывания;
- Infrastructure as Code;
- централизованный мониторинг;
- централизованное логирование;
- distributed tracing;
- стандартизация сервисов;
- единые шаблоны CI/CD;
- единые требования к health checks.

---

# 15.9 R-06. Компрометация пользовательских данных

## Описание

Система обрабатывает:

- данные профиля;
- историю тренировок;
- данные спортивных устройств;
- сведения о местоположении и маршрутах;
- социальную активность;
- данные о спортивных результатах.

Некоторые из этих данных могут быть чувствительными с точки зрения приватности.

## Основные угрозы

- несанкционированный доступ;
- компрометация учётной записи;
- утечка данных;
- неправильная настройка доступа;
- компрометация внешней интеграции.

## Меры снижения риска

- централизованная аутентификация;
- авторизация на уровне API и бизнес-операций;
- минимизация хранимых данных;
- шифрование;
- защищённые каналы;
- аудит;
- ограничение доступа сервисов;
- изоляция баз данных;
- безопасное управление секретами.

---

# 15.10 R-07. Интеграция сторонних устройств

## Описание

Система должна поддерживать подключение различных спортивных устройств. :contentReference[oaicite:5]{index=5}

Различные производители могут использовать:

- разные протоколы;
- разные форматы данных;
- разные механизмы авторизации;
- различные ограничения API.

## Архитектурный риск

Добавление нового производителя может потребовать изменений в системе.

## Принятое решение

Использовать отдельный слой интеграции устройств:

```text
External Devices
      │
      ▼
Device Integration Layer
      │
      ▼
Normalized Telemetry
      │
      ▼
Internal Services
```

Таким образом, внутренняя система работает с унифицированной моделью телеметрии.

---

# 15.11 R-08. Зависимость от внешних систем

Система интегрируется с существующими приложениями компании, а также использует внешние устройства и промоакции.

## Риск

Недоступность внешней системы не должна приводить к недоступности всей платформы.

## Меры

- асинхронное взаимодействие там, где это возможно;
- timeout;
- retry;
- circuit breaker;
- локальное кэширование;
- graceful degradation.

Например, отсутствие системы промоакций не должно препятствовать проведению тренировки.

---

# 15.12 R-09. Рост инфраструктурных расходов

## Описание

Горизонтальное масштабирование и большое количество сервисов повышают потребление вычислительных ресурсов.

Особенно быстро могут расти:

- хранилища телеметрии;
- базы тренировок;
- Event Bus;
- аналитическое хранилище;
- инфраструктура мониторинга и логирования.

## Меры

- независимое масштабирование;
- автоматическое масштабирование;
- lifecycle policy для данных;
- разделение hot/warm/cold data;
- контроль retention;
- мониторинг стоимости;
- регулярная оптимизация потребления ресурсов.

---

# 15.13 R-10. Сложность диагностики распределённых сценариев

Один пользовательский сценарий может проходить через множество сервисов:

```text
Mobile App
   │
   ▼
Workout
   │
   ▼
Event Bus
   │
   ├──► Analytics
   ├──► Competition
   ├──► Recommendation
   └──► Notification
```

При возникновении ошибки необходимо определить:

- где она произошла;
- какое событие стало причиной;
- какой сервис не обработал сообщение;
- на каком этапе произошла задержка.

## Меры

Для каждого запроса и события использовать:

- correlation ID;
- trace ID;
- структурированные логи;
- технические метрики;
- бизнес-метрики;
- distributed tracing.

Наблюдаемость не является одним из трёх главных атрибутов качества всей системы, однако для распределённой архитектуры она является критическим локальным атрибутом.

---

# 15.14 R-11. Ошибки повторной обработки событий

## Описание

Event-driven архитектура предполагает возможность повторной доставки сообщений.

Например:

```text
WorkoutCompleted
      │
      ▼
Competition Service
      │
      ├── processing
      │
      ├── timeout
      │
      └── retry
             │
             ▼
       повторная доставка
```

Без идемпотентности возможно двойное начисление результата.

## Меры

Каждое событие должно иметь уникальный идентификатор.

Consumer должен хранить информацию о уже обработанных событиях или иметь иной механизм обеспечения идемпотентности.

---

# 15.15 R-12. Риск избыточной декомпозиции

## Описание

Микросервисная архитектура создаёт риск чрезмерного дробления системы.

Например, выделение каждого небольшого функционального блока в отдельный сервис может привести к:

- большому количеству сетевых взаимодействий;
- увеличению инфраструктурных расходов;
- усложнению разработки;
- усложнению локального тестирования;
- снижению скорости развития продукта.

## Меры

Границы сервисов должны определяться прежде всего:

- бизнес-доменами;
- владением данными;
- независимостью масштабирования;
- независимостью жизненного цикла;
- различиями в требованиях к доступности и нагрузке.

Не следует создавать отдельный сервис только потому, что функциональность логически выделяется в коде.

# 15.16 Основные архитектурные компромиссы

---

## Компромисс №1. Масштабируемость vs сложность

### Решение

Использование микросервисов и асинхронного взаимодействия.

### Выигрыш

- независимое масштабирование;
- изоляция нагрузки;
- возможность независимо развивать сервисы.

### Цена

- больше компонентов;
- сложнее эксплуатация;
- сложнее диагностика.

### Решение принято потому, что

глобальная аудитория и возможность массовых соревнований делают масштабируемость одним из ключевых требований.

---

# 15.17 Компромисс №2. Eventual Consistency vs простота транзакций

### Решение

Не использовать единую транзакцию между всеми сервисами.

### Выигрыш

- независимость сервисов;
- высокая масштабируемость;
- отсутствие распределённых транзакций.

### Цена

- временная рассогласованность данных;
- необходимость идемпотентности;
- более сложная бизнес-логика.

### Решение принято потому, что

для большинства сценариев системы задержка в обновлении производных данных допустима.

---

# 15.18 Компромисс №3. Доступность vs строгое обновление данных

Например, после завершения тренировки система может сначала сохранить результат, а затем асинхронно обновить:

- аналитику;
- рейтинг;
- достижения;
- рекомендации.

Это позволяет сохранить доступность основного сценария даже при временной недоступности downstream-сервисов.

Цена — пользователь может некоторое время видеть неполную информацию.

---

# 15.19 Компромисс №4. Безопасность vs удобство пользователя

Чем больше механизмов защиты используется, тем больше потенциальных действий требуется от пользователя.

Например:

- подтверждение устройства;
- дополнительные проверки;
- ограничения доступа;
- управление разрешениями.

Система должна найти баланс между уровнем защиты и пользовательским опытом.

При этом для данных спортивной активности и персональных данных приоритет отдаётся безопасности.

---

# 15.20 Компромисс №5. Универсальность интеграций vs сложность интеграционного слоя

Поддержка большого количества спортивных устройств повышает ценность продукта.

Однако каждый новый тип устройства увеличивает:

- количество интеграций;
- требования к тестированию;
- количество потенциальных ошибок;
- стоимость сопровождения.

Поэтому используется унифицированная внутренняя модель телеметрии и отдельный слой интеграции.

---

# 15.21 Компромисс №6. Быстрое развитие vs архитектурная зрелость

Компания располагает большим штатом разработчиков и готова адаптировать новые технологии для экспериментальных приложений. :contentReference[oaicite:7]{index=7}

Однако применение большого количества новых технологий одновременно увеличивает технический риск.

Поэтому рекомендуется:

- использовать проверенные архитектурные паттерны;
- внедрять новые технологии изолированно;
- проводить технические пилоты;
- не связывать критичные бизнес-сценарии с экспериментальными компонентами без необходимости.
