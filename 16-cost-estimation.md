# 16. Стоимость владения системой

## 16.1 Цель расчёта

Цель расчёта — оценить порядок затрат на вычислительную инфраструктуру системы в:

- первый год;
- второй год;
- пятый год.

Расчёт учитывает рост:

- пользовательской базы;
- количества тренировок;
- объёма телеметрии;
- объёма хранимых данных;
- количества запросов;
- количества событий в Event Bus;
- требований к вычислительным ресурсам;
- инфраструктуры мониторинга и резервирования.

Расчёт является архитектурной оценкой и используется для сравнения масштаба затрат между этапами развития системы.

---

# 16.2 Базовый сценарий роста

Для базового сценария принимается следующий рост пользовательской базы.

| Показатель | 1-й год | 2-й год | 5-й год |
|---|---:|---:|---:|
| Зарегистрированные пользователи | 1 млн | 3 млн | 10 млн |
| MAU | 600 тыс. | 1,8 млн | 6 млн |
| DAU | 120 тыс. | 360 тыс. | 1,2 млн |
| Среднее тренировок на MAU в неделю | 3 | 3 | 3 |
| Тренировок в год | ~94 млн | ~281 млн | ~936 млн |

Принятое соотношение:

```text
MAU ≈ 60% зарегистрированных пользователей

DAU ≈ 20% зарегистрированных пользователей
```

---

# 16.3 Расчёт объёма телеметрии

Для оценки объёма телеметрии принимаются следующие допущения:

| Параметр | Значение |
|---|---:|
| Средняя продолжительность тренировки | 1 час |
| Частота телеметрии | 1 событие / 5 секунд |
| Размер одного нормализованного события | 100 байт |
| Тренировок на пользователя | 3 / неделю |

Количество событий на одну тренировку:

```text
3600 / 5 = 720 событий
```

Объём телеметрии:

```text
720 × 100 байт = 72 КБ / тренировка
```

Количество тренировок пользователя в год:

```text
3 × 52 = 156 тренировок
```

Годовой объём телеметрии:

```text
72 КБ × 156 ≈ 11,2 МБ / активного пользователя / год
```

для расчёта принимается:

> **15 МБ данных на одного активного пользователя в год.**

# 16.5 Какие инфраструктурные ресурсы учитываются

Стоимость системы разбивается на следующие основные категории.

| Категория | Назначение |
|---|---|
| Compute | Запуск микросервисов и фоновых обработчиков |
| Database | Операционные базы данных сервисов |
| Event Bus | Передача и хранение событий |
| Object Storage | Архив телеметрии и больших данных |
| Analytics | Обработка аналитических данных |
| Cache | Кэширование часто используемых данных |
| Network | Передача данных между компонентами |
| Load Balancing | Распределение пользовательской нагрузки |
| Monitoring | Метрики и мониторинг |
| Logging | Хранение технических логов |
| Backup / DR | Резервное копирование и восстановление |

# 16.6 Расчёт вычислительной инфраструктуры

Система должна поддерживать горизонтальное масштабирование.

Поэтому количество вычислительных ресурсов определяется не только средним количеством пользователей, но и пиковыми нагрузками.

Особенно важными являются:

- одновременные тренировки;
- обработка телеметрии;
- массовые соревнования;
- пересчёт рейтингов;
- массовая отправка уведомлений.

Для базового сценария принимается следующая оценка.

| Компонент | 1-й год | 2-й год | 5-й год |
|---|---:|---:|---:|
| Business Services | 12–16 CPU | 30–40 CPU | 100–140 CPU |
| Event processing | 8–12 CPU | 20–30 CPU | 80–120 CPU |
| Analytics | 8 CPU | 20 CPU | 80 CPU |
| Integration | 4 CPU | 8 CPU | 20 CPU |
| Monitoring / Logging | 4 CPU | 8 CPU | 20 CPU |
| Резерв мощности | ~30% | ~30% | ~30% |

# 16.7 Базы данных

Каждый бизнес-сервис владеет собственным хранилищем.

Поэтому рост стоимости БД связан не только с объёмом данных, но и с необходимостью:

- высокой доступности;
- репликации;
- резервного копирования;
- масштабирования;
- хранения индексов.

При оценке необходимо учитывать не только размер бизнес-данных.

Для архитектурной оценки принимается коэффициент:

```text
Итоговое хранилище БД ≈ 2,0–2,5 × объём исходных данных
```

# 16.8 Event Bus

Количество сообщений растёт вместе с количеством тренировок и действий пользователей.

Одна завершённая тренировка может приводить к появлению нескольких событий:

```text
WorkoutCompleted
        │
        ├──► Analytics
        ├──► Competition
        ├──► Recommendation
        ├──► Achievement
        └──► Notification
```

Поэтому количество внутренних событий может значительно превышать количество исходных пользовательских операций.

Для расчёта принимается коэффициент:

```text
≈ 5–8 внутренних событий
на одну завершённую тренировку
```

Это приводит к существенному росту требований к Event Bus к пятому году.

---

# 16.9 Хранение телеметрии

Телеметрия является наиболее быстрорастущим типом данных.

Архитектурно целесообразно разделить данные по сроку хранения.

### Hot data

Используется для:

- текущих тренировок;
- последних результатов;
- оперативной аналитики.

Хранится в быстром хранилище.

### Warm data

Используется для:

- истории тренировок;
- сравнений;
- аналитики.

Хранится в более дешёвом storage.

### Cold data

Используется для:

- долгосрочной истории;
- аналитических задач;
- восстановления.

Хранится в дешёвом объектном хранилище.

Такой подход позволяет не хранить всю историю в наиболее дорогом и быстром хранилище.

# 16.11 Стоимость второго года

Ко второму году пользовательская база увеличивается примерно в три раза относительно первого года.

Однако инфраструктурные расходы не обязаны увеличиваться пропорционально.

Это связано с:

- более эффективным использованием ресурсов;
- горизонтальным масштабированием;
- кэшированием;
- оптимизацией хранения;
- переходом части данных в более дешёвые storage-классы.

Оценка:

```text
2000000 × 12 × 0,9  = 43 200 000
```

# 16.12 Стоимость пятого года

К пятому году система работает уже в глобальном масштабе.

Расчётная пользовательская база:

```text
10 млн зарегистрированных
6 млн MAU
1,2 млн DAU
```

Накопленный объём данных:

```text
≈ 180 ТБ исходных данных
```

С учётом:

- репликации;
- индексов;
- резервных копий;
- аналитических копий;
- Event Bus retention;

фактический объём инфраструктурного хранения может достигать нескольких сотен терабайт.

Оценка:

| Категория | Оценка в месяц |
|---|---:|
| Compute | 3 200 000 |
| Database | 2 400 000 |
| Event Bus | 1 600 000 |
| Storage | 1 200 000 |
| Analytics | 2 000 000 |
| Network / LB / CDN | 1 600 000 |
| Monitoring / Logging | 1 200 000 |
| Backup / DR | 1 200 00 |
| Резерв | 1 600 000 |
| **Итого** | **~16 000 000 / месяц** |

Год:

```text
16 000 000 × 12 = 192 000 000
```

# 16.15 Факторы, способные существенно изменить стоимость

Наиболее сильное влияние на стоимость оказывают:

1. Количество MAU.
2. Количество тренировок на пользователя.
3. Продолжительность тренировки.
4. Частота отправки телеметрии.
5. Размер телеметрического события.
6. Срок хранения истории.
7. Требования к репликации.
8. Пиковая нагрузка во время соревнований.
9. Объём аналитических расчётов.
10. Объём и срок хранения логов.
