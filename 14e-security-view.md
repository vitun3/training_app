# 14.5 Представление безопасности

## 14.5.1 Назначение

Представление безопасности описывает основные механизмы защиты пользователей, данных и межсервисного взаимодействия.

Основными целями являются:

- защита пользовательских данных;
- предотвращение несанкционированного доступа;
- безопасное взаимодействие сервисов;
- контроль доступа;
- аудит критичных операций.

---

# 14.5.2 Модель аутентификации

Аутентификация выполняется централизованно.

Упрощённый поток:

```text
User
 │
 ▼
Mobile App
 │
 ▼
Identity Provider
 │
 │ Access Token
 ▼
API Gateway
 │
 ▼
Business Services
```

Мобильное приложение не должно самостоятельно реализовывать механизмы хранения и проверки пользовательских паролей.

---

# 14.5.3 Авторизация

После успешной аутентификации система определяет права пользователя.

Авторизация должна выполняться на основании:

- идентификатора пользователя;
- ролей;
- разрешений;
- принадлежности к ресурсам;
- контекста операции.

Например:

```text
User
 │
 ├── authenticated?
 │
 ▼
Access Token
 │
 ├── valid?
 │
 ├── required scope?
 │
 └── access to resource?
 │
 ▼
Business Operation
```

---

# 14.5.4 Защита данных

Для защиты данных используются следующие принципы:

### Данные при передаче

Передача данных между клиентом, сервисами и внешними системами должна осуществляться по защищённым каналам.

### Данные при хранении

Конфиденциальные данные должны храниться в защищённом виде.

### Минимизация данных

Каждый сервис должен хранить только те данные, которые необходимы ему для выполнения собственных функций.

---

# 14.5.5 Изоляция сервисов

Каждый сервис имеет собственную область ответственности и собственное хранилище данных.

Запрещается:

```text
Service A ───────► Database B
```

Допустимые варианты:

```text
Service A ──API──► Service B
```

или:

```text
Service A ──Event──► Event Bus ──► Service B
```

Это ограничивает потенциальный радиус распространения ошибки или компрометации одного компонента.

---

# 14.5.6 Безопасность спортивных устройств

Подключение спортивных устройств должно выполняться с проверкой:

- идентификатора устройства;
- принадлежности устройства пользователю;
- прав доступа;
- корректности передаваемых данных.

Устройство не должно получать прямой доступ к внутренним сервисам платформы.

Архитектурно взаимодействие осуществляется через специализированный сервис интеграции устройств.

---

# 14.5.7 Защита внешних интеграций

Внешние системы изолируются от внутренней бизнес-логики посредством интеграционного слоя.

```text
Internal Services
       │
       ▼
Integration Layer
       │
       ├────► Existing Company Apps
       │
       ├────► Promotion System
       │
       └────► External Device APIs
```

Это позволяет:

- контролировать внешний трафик;
- изолировать изменения внешних API;
- ограничить доступ внешних систем;
- централизованно регистрировать интеграционные операции.

---

# 14.5.8 Аудит

Для критичных операций должен формироваться аудит.

В частности:

- вход пользователя;
- изменение критичных настроек;
- изменение данных профиля;
- подключение устройства;
- изменение прав доступа;
- административные операции;
- операции с персональными данными.

Аудит должен быть отделён от обычных технических логов и защищён от несанкционированного изменения.
